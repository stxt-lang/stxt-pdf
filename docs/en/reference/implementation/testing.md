# Tests

```bash
mvn test                                   # compiles, runs all the tests and leaves the coverage in target/site/jacoco/index.html
mvn test -Dtest=ValueParserTest            # one class
mvn test -Dtest='TrackSizingTest#name'     # one method
```

`mvn test` writes nothing in `test/`: what the tests generate goes to `target/`.

## Unit and layout tests

JUnit 5. One test per pure piece, in the same package as the class (`src/test/java/dev/stxt/pdf/...`). The names of the
test methods are in English and in camelCase (`autoMarginsCenter`).

The test documents are read with `DocumentReader`, which validates against the schema: a test of a model rule thus checks
that the schema does not detect it first. The tests of an algorithm lay out small documents with `LayoutFixture` (A4, with a
page area of 515 × 762 pt from (40, 40), and `rect(id)` gives the border box in page coordinates). The fixture declares in
`For element: Document` `Font: IBM Plex Sans` and `Size: 10` (`Docs.mergeStyles` merges the `Styles` of the test with that one and wraps the
content in a `Section`). With `FixedMetrics`, each character measures 5 pt with `Size: 10`. `layOutPaged(height, ...)` paginates (with
180 pt of height, the page area measures 100) and `rect(page, id)` / `has(page, id)` look at a specific page. A layout
test cannot overflow: overflows go to the error catalog.

The test cases that are not code are in `test/` (`golden/`, `errors/`, `examples/`, `spec/`), which the tests read by
disk path and not from the classpath. The images of the tests are in the resources folder of the repository,
`resources/images/test/` (`wide.png` 150 × 75 pt, `tall.jpg` 90 × 120, `square.png` 30 × 30, `shapes.svg` 150 × 75 and
`label.svg` 120 × 36, and `drawing.gif`, `broken.png` and the `bad-*.svg` for the errors), because the layout tests, the
error catalog and the golden cases use the default folder.

## Reference tests (`GoldenTest`)

Each folder of `test/golden/NN-name/` has `input.stxt` and `expected.stxt` ([the dump](#the-dump)). The rectangles
are compared with a tolerance of 0.01 pt. The expected result is computed by hand following the reference, as in the
[complete example](../common/complete-example.md), and is never updated. Each case writes a debug SVG in
`target/golden-svg/`, and `output.pdf` and one `page-N.png` per page (with the outlines of the boxes and the real metrics) in
`target/reference/golden/NN-name/`. Each image is compared with the versioned `page-N.png` in the folder of the case: if
it changes beyond the antialiasing, which varies between machines (16 per channel), or there are extra or missing pages, the case **fails**
with the path of the new images. If the change is the intended one, it is accepted with `-Dgolden.update=true`, which rewrites only
those that change. The CI uploads `target/reference` when it fails.

> **Decision:** a reference image that changes makes the test fail, and it is only accepted by hand: this way a change does not go
> unseen in `git status`. *Rejected alternative:* rewriting them on each run and having the CI check the tree, which
> warns but does not say which page and does not leave the images at hand.

## Examples (`ExamplesTest`)

Each folder of `test/examples/NN-name/` is a complete document written in two languages, each one in its subfolder:
Spanish (`es/`), the original, and English (`en/`), its mirror. Both versions share the `styles.stxt` of the folder of the
example. Each language has its `input.stxt`, one `page-N.png` per page (versioned, without outlines, at 110 dpi), the
`output.pdf` and an `expected.stxt` with the dump of the boxes with `Id`. They are laid out with the **real metrics** and the `resources/` folder, the contrast of the text is checked, and the PDF is
validated with veraPDF, as PDF/UA-1 and also written as PDF/UA-2. The
dump is not computed by hand: it is a snapshot generated with `-Dexamples.update=true`, which also accepts the images that
change and rewrites the `output.pdf`, and it is reviewed by looking at the images. `-Dexamples.only` limits the run to an example
(`01-invoice`), a language (`en`) or both (`01-invoice/en`). A test also checks that the English version mirrors the
Spanish one: the same nodes in the same order, the same `Id` and `Style`, the same image in its language folder and
`Language: en`. Only the texts change. The images of the examples are in `resources/images/examples/` and are generated by
`java tools/ExampleImages.java` (Java2D, without third-party files). Those with text (the charts of the report, the
figures of the manual and the seal of the certificate) are generated once per language, in `es/` and `en/`.

> **Decision:** each example is in the two languages of the documentation, with a single `styles.stxt` for both: the
> document carries the content and the styles are the same in any language. *Rejected alternative:* one tree of examples
> per language (`test/examples/es/`, `test/examples/en/`), which duplicates the styles and forces keeping them equal.

> **Decision:** the examples are laid out with the real metrics and their dump is a snapshot that is reviewed by looking at the
> images: with real text and fonts, computing it by hand makes no sense. *Rejected alternative:* comparing only the
> images, which does not detect one-point changes.

> **Decision:** the `output.pdf` of each example is versioned so that it can be opened from the repository, but it is only written with
> `-Dexamples.update=true` and is not compared: it carries the date and an identifier that change on each run. What is watched
> is the images and the dump.

> **Decision:** the images of the examples are generated by a program (`tools/ExampleImages.java`): there are no third-party
> files or rights to respect, and they can be changed by adjusting the program. The fonts are IBM Plex Sans, Serif and Mono,
> with their OFL license. *Rejected alternative:* images from free stock libraries, which would have to be credited and cannot be
> regenerated.

## Documents of the documentation (`DocumentationExamplesTest`)

Each complete document (`Document (dev.stxt.pdf):` in a code block) of the [manual](../../manual/README.md) and of the
reference is laid out with the real metrics, its contrast is checked and it is written to PDF, which must conform to PDF/UA-1 and,
written as PDF/UA-2, to PDF/UA-2 according to veraPDF. The PDF is left
in `target/reference/docs/`. The [complete example](../common/complete-example.md) must be `test/spec/report.stxt` without its header
comments. This way no example in the documentation stops working unnoticed.

## Error catalog (`ErrorCatalogTest`)

`test/errors/<group>/<code>.<description>.stxt` is a real STXT document, one file per case, in the folder of its
family (`document`, `schema`, `values`, `structure`, `headings`, `lists`, `tables`, `columns`, `markdown`, `images`,
`references`, `links`, `contents`, `sections`, `styles`, `combinations`, `overflow`, `fonts` and `limits`, and the codes
of `stxt-core` go in `schema`). The first three lines are `# Case:` (description), `# Code:` and `# Line:` comments, and the
expected line is that of the file itself, header included (the first line of the document is line 4). It is laid out with the
real metrics. `everyCodeHasACase` requires one case for each `ErrorCode` except those in `UNCOVERED`. The layout tests test
the valid cases, and the invalid ones go to the catalog.

> **Decision:** the catalog has one file per case, a real STXT document, so that it can be opened and validated in the
> editor without counting lines from an embedded block. *Rejected alternative:* one file per group with the documents
> embedded.

## Properties, determinism and mutation

- **Properties:** `ValueParserPropertiesTest`, `LineBreakerPropertiesTest` and `FragmentationPropertiesTest` test
  properties with thousands of random inputs from a `Random` with a fixed seed (a failure repeats) and without new libraries.
- **Determinism:** `CrossJvmDeterminismTest` checks that a child JVM gives the same PDF for each example and golden case.
- **Threads:** `ConcurrentConversionTest` and `EngineContractTest` ([Using from Java](api.md#threads)).
- **Architecture:** `ArchitectureTest` checks the dependencies between packages ([Architecture](../architecture.md)).
- **Mutation:** the `pit` profile of the `pom.xml` runs PIT over `layout` and `fragment`
  (`mvn -Ppit test-compile org.pitest:pitest-maven:mutationCoverage`, about 13 min, with the report in
  `target/pit-reports/`). It is not in
  the CI: it is an occasional pass to see whether the asserts measure anything. It leaves out the tests that write in shared folders
  of `target/` or start another JVM.
- **Performance:** the tests with `@Tag("perf")` are not run by `mvn test`. They are run with
  `mvn test -Dgroups=perf -DexcludedGroups=none -Dtest=...`. The measurement probes are in [`tools/qa/`](../../../../tools/qa).

## Continuous integration

`.github/workflows/ci.yml` runs `mvn test` with JDK 17 and 21 and with the JVM in Turkish (which checks that the locale of the JVM does not
change anything and that the tree is left clean), and, in the daily run and when run by hand, on Windows.

## The dump

The engine can dump the result in STXT (`StxtDump`), which is the format of the `expected.stxt`. Each `Rect` is the border
box in **absolute page coordinates**: `x y width height`, in pt, with up to two decimals.

```
Result:
    Page: 1
        Fragment: header
            Rect: 40 10 515 20
        Fragment: body
            Rect: 40 80 515 300
            Fragment: side
                Rect: 40 80 150 120
```

The dumps have no namespace and are read with `STXT.rawParser()`.

- Only the boxes with `Id` are dumped, and the descendants with `Id` are nested inside.
- The marker of a `List item` with `Id` is dumped inside the item as `Marker: 3.`, with its `Rect`.
- An `Overlay` is nested inside its reference container, after its in-flow children, and not inside its parent.
- The columns of a `Columns` have no fragment: their children are nested inside the `Columns`, and a box split across two
  columns appears twice on the same page.
- The coordinates are those of the page of its section. A `Section` is not dumped as a box, and the `Page overlay` of the document
  appear before those of the section.
- The boxes without `Id` can be included for debugging.
- The text lines, the runs, the links, the element type, the appearance (backgrounds, borders, corners) and
  the rotation are not dumped. The `Rect` of a rotated positioned element is the unrotated one. That of a box rotated in flow is the rectangle it
  occupies, and those of its descendants, unrotated.

> **Decision:** the runs are not dumped: they are tested with layout and painting tests. *Rejected alternative:* dumping the
> lines with their runs.

> **Decision:** the `Rect` of a rotated positioned element is the unrotated one, like that of a link or a background, because its rotation does not
> change the layout. That of a box rotated in flow is the rectangle it occupies, which is what its rotation changes in the layout.
